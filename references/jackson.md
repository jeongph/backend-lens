# Jackson 참조

적용 버전: Spring Boot 3.x(Jackson 2.x)와 Spring Boot 4.x(Jackson 3.x). 버전에 따라 결론이 다른 곳은 항목 안에 버전을 적었다.

## Jackson 3 패키지 이동과 조용히 무시되는 어노테이션

- 의심할 코드: Spring Boot 4로 올리는 변경에서 `com.fasterxml.jackson.databind.annotation` 패키지의 `@JsonSerialize`, `@JsonDeserialize`, `@JsonNaming`, `@JsonPOJOBuilder` import가 그대로 남아 있는 것. 빌드 파일에 `com.fasterxml.jackson.core:jackson-databind`가 직접 의존성이나 전이 의존성으로 남아 있는 것. 옛 `Jackson2ObjectMapperBuilderCustomizer`나 `@JsonComponent`를 살리려고 `spring-boot-jackson2` 모듈만 더하는 것.
- 실패 시나리오: Jackson 3의 그룹과 패키지는 `tools.jackson`이고, `jackson-annotations`(`@JsonProperty`, `@JsonFormat`, `@JsonIgnore` 등)만 `com.fasterxml.jackson.annotation`에 남는다. Jackson 2 databind가 클래스패스에 있으면 옛 패키지의 databind 어노테이션은 컴파일되지만 Jackson 3가 경고 없이 무시한다. 예를 들어 `Order.id`에 단 `@JsonSerialize(using = ToStringSerializer.class)`가 무시되면 문자열로 나가던 ID가 숫자로 바뀌어 웹 클라이언트에서 정밀도가 깨진다. `@JsonNaming`이 무시되면 그 DTO의 응답 필드 이름이 모두 바뀐다. `spring-boot-jackson2`만 더하면 옛 customizer와 직렬화기는 Jackson 2 매퍼에만 걸리고, HTTP 변환기는 기본값(`spring.http.converters.preferred-json-mapper=jackson`)대로 Jackson 3를 쓰므로 응답에 반영되지 않는다.
- 문제가 아닌 경우: `com.fasterxml.jackson.annotation` 패키지의 어노테이션은 Jackson 3에서도 그대로 동작한다. `spring-boot-jackson2` 모듈과 함께 `spring.http.converters.preferred-json-mapper=jackson2`로 HTTP 변환기를 Jackson 2에 둔 프로젝트라면 옛 패키지가 맞다.
- 고치는 방향: databind 어노테이션 import를 `tools.jackson.databind.annotation`으로 바꾸고 해당 DTO의 직렬화 결과를 테스트로 고정한다. Boot 4에서 `Jackson2ObjectMapperBuilderCustomizer`는 `JsonMapperBuilderCustomizer`로, `@JsonComponent`는 `@JacksonComponent`로 옮긴다.

## Boot 4 기본값 변경으로 달라지는 응답

- 의심할 코드: 빌드 파일에서 `org.springframework.boot` 버전을 3.x에서 4.x로 올리는 변경. 그 프로젝트의 응답 DTO에 다음이 있는 것. `@JsonPropertyOrder` 없이 기본 생성자와 setter, getter로 된 클래스, `toString()`을 재정의한 enum(`ChronoUnit` 같은 JDK enum 포함), `java.util.Date`나 `Calendar` 필드, `java.time.Month` 필드, 앞 두 글자 안에 대문자가 있는 필드(`xCoord`), `get` 뒤가 대문자 두 개 이상으로 시작하는 getter(`getURL()`), `get`이나 `set` 바로 뒤가 소문자인 접근자(`getxCoord()`). `JsonMapper.builder()`로 매퍼를 직접 만드는 코드도 같다.
- 실패 시나리오: Boot 4는 `spring.jackson.use-jackson2-defaults`가 false(기본)이면 Jackson 3 기본값을 그대로 쓴다. 생성자로 받지 않는 속성은 알파벳 순으로 나가고, enum은 `name()` 대신 `toString()` 값으로 나가며, `Date`와 `Calendar`의 UTC 표기는 `+00:00`에서 `Z`로 바뀐다. `Month`는 일반 enum이 아니라 날짜 타입으로 다뤄져 `"MARCH"` 대신 숫자로 나간다. 필드 이름 추론도 바뀐다. Jackson 3는 표준 빈 이름 규칙만 쓰므로(USE_STD_BEAN_NAMING 제거) `getURL()`은 `"url"`에서 `"URL"`로 바뀌고, 앞쪽 대문자 필드는 FIX_FIELD_NAME_UPPER_CASE_PREFIX 때문에 이름이 달라질 수 있다. `get`이나 `set` 바로 뒤가 소문자인 접근자는 Jackson 3가 접근자로 보지 않으므로, 그 속성이 응답에서 빠지고 요청 값도 오류 없이 버려진다. 속성이 없는 객체는 오류 대신 `{}`로 나간다. 필드 이름이나 타입이 바뀐 응답을 읽는 구버전 앱, 응답 문자열이나 필드 순서를 그대로 비교하는 클라이언트와 서명 검증, 오프셋 문자열을 잘라 쓰는 클라이언트가 깨진다.
- 문제가 아닌 경우: Boot 3가 Jackson 2에 걸던 설정(FAIL_ON_UNKNOWN_PROPERTIES, WRITE_DATES_AS_TIMESTAMPS, WRITE_DURATIONS_AS_TIMESTAMPS, DEFAULT_VIEW_INCLUSION 끄기)은 Jackson 3의 기본값과 같다. 그래서 모르는 요청 필드를 무시하는 동작과 날짜와 기간을 ISO-8601 문자열로 쓰는 동작은 Boot 4에서도 그대로다. record와 생성자로 받는 속성은 SORT_CREATOR_PROPERTIES_FIRST(기본 켜짐)에 따라 선언 순서로 맨 앞에 나오므로 알파벳 정렬 대상이 아니다. `toString()`을 재정의하지 않은 enum, `@JsonValue`나 `@JsonPropertyOrder`로 고정한 값, `Month`를 뺀 `java.time`의 날짜와 시간 값 타입은 이 변경의 영향을 받지 않는다. 다만 `java.time.temporal.ChronoUnit`처럼 `toString()`을 재정의한 JDK enum은 enum 규칙대로 바뀐다(`"DAYS"`가 `"Days"`로).
- 고치는 방향: 업그레이드 전에 대표 응답을 Boot 3 결과와 비교하는 직렬화 테스트를 두고, 다른 부분만 `@JsonPropertyOrder`, `@JsonValue`, `@JsonProperty`, `spring.jackson.*` 기능 설정으로 되돌린다. `spring.jackson.use-jackson2-defaults=true`로 한꺼번에 맞출 수 있지만 Boot 3와 같아진다고 보지 않는다. 이 모드는 Jackson 3.0.x(Boot 4.0.0부터 4.0.3까지)에서 `Date`의 UTC 표기를 되돌리지 않고, `getURL()`과 소문자 접근자 같은 이름 규칙은 어느 버전에서도 되돌리지 않는다(Jackson 3.1.4 이후에는 `getXCoord()`가 Boot 3와도 Boot 4 기본과도 다른 `"XCoord"`가 된다). 또 ONE_BASED_MONTHS를 꺼서 `Month`를 0부터 세는 숫자로 쓰고, DETECT_PARAMETER_NAMES를 끈다(아래 요청 항목 참고).

## Boot 4 기본값 변경으로 실패하는 요청

- 의심할 코드: Boot 4로 올리는 변경에서 요청 DTO나 record에 원시 타입(`int`, `long`, `boolean`) 필드나 생성자 파라미터가 있는 것. 기본 생성자와 public 매개변수 생성자를 함께 가진 요청 DTO. `use-jackson2-defaults`를 켤 때 `@JsonCreator` 없는 단일 생성자로 받는 불변 클래스. 요청에 쓰는 enum이 `toString()`을 재정의한 것. setter 없이 getter만 있는 컬렉션 속성, 생성자 없이 final 필드로 받는 클래스. Boot 4.0.0부터 4.0.5 사이 버전에서 `spring.jackson.use-jackson2-defaults=true`를 켜는 것.
- 실패 시나리오: Jackson 3는 FAIL_ON_NULL_FOR_PRIMITIVES와 FAIL_ON_TRAILING_TOKENS를 기본으로 켠다. `{"quantity": null}`을 보내던 구버전 앱의 요청은 Boot 3에서는 0으로 들어갔지만 Boot 4에서는 역직렬화가 실패해 400(HttpMessageNotReadableException)이 된다. 생성자나 record로 받는 원시 타입 값이 요청에서 빠져도 실패한다(Jackson 3.0과 3.1, 즉 Boot 4.0부터 4.2까지의 관리 버전 기준. Jackson 3.2부터는 FAIL_ON_MISSING_CREATOR_PROPERTIES를 켜지 않는 한 빠진 값이 기본값으로 채워지고 명시적 null만 실패한다). Jackson 3는 기본 생성자가 있어도 public 매개변수 생성자가 하나 있고 파라미터 이름을 알 수 있으면 그 생성자로 객체를 만들므로(databind#5318), Boot 3에서 기본 생성자와 setter로 받던 DTO도 이 경우에 들어간다. 원시 타입 값이 빠지면(Jackson 3.1 이하) 400이 되고, 래퍼 타입은 필드 초기값 대신 null이 들어가며 setter 로직을 건너뛴다. `use-jackson2-defaults=true`는 DETECT_PARAMETER_NAMES를 끄므로, Boot 3에서 동작하던 `@JsonCreator` 없는 단일 생성자 불변 클래스가 생성자를 찾지 못해 500이 된다(record는 영향이 없다). 본문 뒤에 다른 내용이 이어 붙은 요청도 400이다. READ_ENUMS_USING_TO_STRING도 켜지므로 `toString()`을 재정의한 enum은 그 값만 받고, `name()` 값(`"PAID"`)을 보내던 클라이언트는 400을 받는다. USE_GETTERS_AS_SETTERS와 ALLOW_FINAL_FIELDS_AS_MUTATORS가 꺼져서, getter만 있는 컬렉션과 final 필드에는 요청 값이 오류 없이 들어가지 않는다. 또 Boot 4.0.0부터 4.0.5까지는 `use-jackson2-defaults=true`가 FAIL_ON_UNKNOWN_PROPERTIES를 켜서, 서버 DTO에 없는 필드를 보내는 클라이언트 요청이 모두 400이 된다(4.0.6에서 Boot 3와 같게 고쳤다).
- 문제가 아닌 경우: 래퍼 타입(`Integer`, `Long`, `Boolean`) 필드에 null이 들어가는 것은 Boot 3와 같다. public 매개변수 생성자가 없는 클래스는 기본 생성자로 만들어지므로, 값이 빠진 필드에는 필드 초기값이 그대로 남는다. 모르는 필드를 무시하는 동작은 Boot 3와 Boot 4의 기본 설정이 같으므로, Boot 4.0.6 이상이거나 `use-jackson2-defaults`를 켜지 않았다면 모르는 필드 때문에 400이 나지 않는다. Jackson을 3.2 이상으로 올린 프로젝트에서 원시 타입 값이 요청에서 빠지는 경우(명시적 null은 여전히 실패한다).
- 고치는 방향: null이나 누락이 올 수 있는 요청 값은 래퍼 타입으로 받고 필수 여부는 검증 어노테이션으로 드러낸다. 기존 동작을 당장 지켜야 하면 `spring.jackson.deserialization.fail-on-null-for-primitives=false`, `spring.jackson.datatype.enum.read-enums-using-to-string=false`처럼 기능을 하나씩 되돌린다. Boot 4.0.x는 4.0.6 이상을 쓴다.

## 전역 Jackson 설정과 매퍼 빈 교체

- 의심할 코드: `application.yml`이나 `application.properties`의 `spring.jackson.*` 변경. `@Bean ObjectMapper`나 `@Bean Jackson2ObjectMapperBuilder`(Boot 3), `@Bean JsonMapper`나 `JsonMapper.Builder`(Boot 4) 추가. `Jackson2ObjectMapperBuilderCustomizer`, `JsonMapperBuilderCustomizer`, Jackson 모듈 빈 추가. Boot 4에서 Jackson 모듈 의존성 추가나 `spring.jackson.find-and-add-modules` 변경. `spring.http.converters.preferred-json-mapper` 변경.
- 실패 시나리오: 자동 구성 매퍼는 Spring MVC의 JSON 변환기와 Boot가 구성한 HTTP 클라이언트가 함께 쓴다. 그래서 설정 한 줄이 diff에 보이지 않는 모든 컨트롤러의 응답과 요청 해석, 다른 서버로 보내는 요청 본문을 한꺼번에 바꾼다. 같은 타입의 매퍼 빈(Boot 3는 `ObjectMapper`, Boot 4는 `JsonMapper`)이나 빌더 빈을 하나라도 정의하면 용도와 상관없이 자동 구성이 모두 꺼진다. 예를 들어 Boot 3에서 메시지 처리용으로 `new ObjectMapper()`를 빈으로 등록하면 HTTP 응답도 그 매퍼로 나간다. 이 매퍼에는 java.time 모듈이 없어서 `LocalDateTime` 같은 필드가 있는 응답은 직렬화에 실패해 500이 되고, Boot가 끄던 FAIL_ON_UNKNOWN_PROPERTIES와 WRITE_DATES_AS_TIMESTAMPS가 Jackson 2 기본값(켜짐)으로 돌아가 모르는 필드를 보내는 요청은 400, `Date`는 숫자가 된다. 이 연쇄는 `new ObjectMapper()`나 `JsonMapper.builder()`로 처음부터 만든 매퍼의 경우다. Spring의 `Jackson2ObjectMapperBuilder`를 새로 만들어 쓴 매퍼는 java.time 모듈이 등록되고 FAIL_ON_UNKNOWN_PROPERTIES는 꺼진 채지만, WRITE_DATES_AS_TIMESTAMPS와 WRITE_DURATIONS_AS_TIMESTAMPS가 Jackson 2 기본값(켜짐)으로 돌아가 날짜와 `Duration`이 숫자로 나간다. 또 Boot의 customizer는 자동 구성 빌더 빈에만 걸리므로 `spring.jackson.*`(property-naming-strategy, default-property-inclusion 등), 사용자 Module 빈, `@JsonComponent`와 `@JsonMixin`이 적용되지 않아 날짜 필드가 없는 응답도 필드 이름과 생략 규칙이 바뀔 수 있다. Boot 3에서 `ObjectMapper` 빈으로 매퍼를 교체하던 코드는 Boot 4로 올리면 교체 효과가 사라진다. 자동 구성 `JsonMapper`가 `@Primary`로 함께 만들어지고 `ObjectMapper`의 하위 타입이라, HTTP 변환기와 `ObjectMapper` 주입 지점이 그 매퍼를 써서 교체 설정이 오류 없이 빠진다. 사용자 빈에도 `@Primary`가 있으면 primary가 둘이라 기동할 때 NoUniqueBeanDefinitionException이 난다. Boot 4는 클래스패스의 Jackson 모듈을 모두 자동 등록하므로(Boot 3는 잘 알려진 모듈만 등록) 의존성 추가만으로 직렬화가 바뀔 수 있다.
- 문제가 아닌 경우: customizer로 같은 변경에서 새로 만든 타입에만 적용되는 직렬화기나 모듈을 더하는 경우. 단 Boot 3에서 consumer를 받지 않는 `modulesToInstall`이나 `modules`로 모듈을 넣으면 기존 모듈을 대체하므로 문제다. 매퍼를 빈으로 등록하지 않고 한 클래스 안에서 지역적으로 만들어 쓰는 경우. 자동 구성 빌더(Boot 3 `Jackson2ObjectMapperBuilder`, Boot 4 `JsonMapper.Builder`)를 주입받아 다른 설정을 더하지 않고 `build()`만 한 매퍼 빈(빌더에 `spring.jackson.*`와 모듈 빈이 이미 적용되어 있어 설정이 유지된다). 빌더에 설정을 더해 build하면 그 설정이 HTTP 응답에도 걸리므로 해당하지 않고, Boot 4에서는 그 빈이 `JsonMapper` 타입이거나 `@Primary`가 없을 때만 해당한다. HTTP 변환기를 `jackson2`로 둔 프로젝트에서 `spring.jackson.*`를 바꾸는 경우(이때 HTTP에는 `spring.jackson2.*`가 적용된다).
- 고치는 방향: 전역 설정을 바꾸기보다 필요한 DTO에 어노테이션을 달아 범위를 좁힌다. 매퍼를 교체하지 말고 customizer로 덧붙이며, 다른 용도의 매퍼는 빈으로 노출하지 않는다. Boot 4에서 매퍼를 교체해야 하면 `ObjectMapper`가 아니라 `JsonMapper` 빈으로 정의한다. 전역으로 바꿔야 하면 대표 응답의 전후 직렬화 결과를 비교하는 테스트를 두고 클라이언트 배포 일정과 맞춘다.

## 필드 이름 변경과 @JsonProperty, @JsonIgnore

- 의심할 코드: 응답이나 요청 DTO의 필드 이름, getter 이름, record 컴포넌트 이름 변경. `@JsonProperty` 값 변경이나 제거. 기존 필드에 `@JsonIgnore` 추가, `@JsonIgnoreProperties` 목록 변경. Jackson 어노테이션(`@JsonIgnore`, `@JsonFormat`, `@JsonSerialize`, `@JsonView` 등)이 달린 private 필드의 이름 변경.
- 실패 시나리오: Jackson은 필드나 getter 이름으로 JSON 이름을 만들므로, 자바 쪽 이름 변경이 곧 API 필드 이름 변경이다. 응답에서는 구버전 앱이 옛 필드를 찾지 못해 빈 값을 보여 주거나 디코딩에 실패한다. 요청에서는 구버전 클라이언트가 보내는 옛 이름이 모르는 속성이 되고, 기본 설정(모르는 속성 무시)에서는 오류 없이 버려져 필드가 null로 들어간다. 그 결과 검증이 있으면 400, 없으면 데이터 누락이 생긴다. `@JsonIgnore`는 getter 하나에만 달아도 속성 전체에 적용되어 응답과 요청 양쪽에서 사라진다.
- 문제가 아닌 경우: `@JsonProperty("orderNo")`처럼 JSON 이름을 명시한 채 자바 이름만 바꾼 경우. Jackson 어노테이션이 없는 private 필드 이름만 바꾸고, 같은 이름의 public getter와 setter가 모두 있으며 그 이름이 그대로인 경우(기본 가시성에서 필드와 getter는 public일 때만 이름을 정한다). private 필드에 Jackson 어노테이션이 있으면 해당하지 않는다. 필드 이름이 곧 어노테이션이 붙는 속성 이름이라, `@JsonIgnore private String password`의 필드만 바꾸면 무시 표시가 새 이름 속성으로 옮겨 가고 getter의 `password`가 응답에 나간다. `@JsonFormat`, `@JsonSerialize`, `@JsonView`가 붙은 필드는 그 자체로 보이는 속성이 되어, 이름을 바꾸면 JSON 필드가 하나 더 생기고 getter 속성의 형식 지정이 빠진다. setter 없이 getter와 private 필드로 요청 값을 받던 클래스도 필드 이름을 바꾸면 요청 값이 버려진다. 어노테이션으로 생성한 접근자와 record 컴포넌트는 이름이 함께 바뀌므로 해당하지 않는다. 같은 변경에서 새로 만든 DTO나 엔드포인트. 같은 변경에서 추가한 필드를 다시 빼는 경우.
- 고치는 방향: 응답은 `@JsonProperty`로 옛 이름을 고정한다. 요청은 `@JsonAlias("oldName")`로 옛 이름도 받는다(직렬화에는 영향이 없다). 필드를 없애야 하면 사용 중단을 먼저 알리고 클라이언트가 옮겨 간 뒤 지운다.
- 출처: https://github.com/FasterXML/jackson-annotations/wiki/Jackson-Annotations, https://github.com/FasterXML/jackson-annotations/blob/2.x/src/main/java/com/fasterxml/jackson/annotation/JsonAlias.java, https://github.com/FasterXML/jackson-databind/wiki/Deserialization-Features, https://github.com/FasterXML/jackson-databind/blob/3.x/src/main/java/tools/jackson/databind/introspect/VisibilityChecker.java, https://github.com/FasterXML/jackson-databind/blob/3.x/src/main/java/tools/jackson/databind/introspect/POJOPropertiesCollector.java, https://github.com/FasterXML/jackson-databind/blob/3.x/src/main/java/tools/jackson/databind/introspect/JacksonAnnotationIntrospector.java

## null 필드 생략과 @JsonInclude

- 의심할 코드: 클래스나 필드에 `@JsonInclude(JsonInclude.Include.NON_NULL)`, `NON_EMPTY`, `NON_DEFAULT`를 추가하거나 제거하는 것. `spring.jackson.default-property-inclusion` 변경.
- 실패 시나리오: `NON_NULL`이면 값이 null인 필드가 키째 빠진다. 키가 있다고 가정하는 웹 코드(`=== null` 비교, `'nickname' in member` 검사)와 키를 필수로 선언한 구버전 앱 모델이 깨진다. `NON_EMPTY`는 빈 문자열과 빈 배열도 빼므로 `items: []`가 사라져 목록을 순회하던 클라이언트가 오류를 낸다. 전역 기본값으로 `NON_DEFAULT`를 쓰면 `0`과 `false`까지 빠진다. 반대로 생략을 없애면 그동안 없던 키가 null로 나타나 null을 허용하지 않는 클라이언트 모델이 실패한다. Boot 4.0.0에서는 `default-property-inclusion`이 Map 안의 값에 적용되지 않았고 4.0.1에서 고쳐졌다.
- 문제가 아닌 경우: 요청으로만 쓰는 DTO에 단 경우(`@JsonInclude`는 직렬화에만 쓰인다). 해당 필드가 항상 값을 갖는 경우. 같은 변경에서 새로 만든 응답.
- 고치는 방향: 기존 응답의 포함 규칙은 바꾸지 않는다. 바꿔야 하면 API 문서에 키 생략 여부를 적고 대표 응답 스냅샷 테스트로 고정한다.
- 출처: https://github.com/FasterXML/jackson-annotations/wiki/Jackson-Annotations, https://github.com/FasterXML/jackson-annotations/blob/2.x/src/main/java/com/fasterxml/jackson/annotation/JsonInclude.java, https://github.com/spring-projects/spring-boot/issues/48343

## enum 직렬화와 모르는 enum 값

- 의심할 코드: 응답이나 요청에 쓰이는 enum의 상수 추가, 이름 변경, 삭제. 기존 enum에 `@JsonValue`나 `@JsonCreator`를 더하거나 바꾸는 것. `@JsonValue`가 있는 enum 상수에 `@JsonAlias`를 달아 옛 값을 받으려는 것. Jackson 3에서 enum의 `toString()` 재정의. `READ_UNKNOWN_ENUM_VALUES_AS_NULL`, `READ_UNKNOWN_ENUM_VALUES_USING_DEFAULT_VALUE`, `@JsonEnumDefaultValue` 추가나 제거(Boot 3는 `spring.jackson.deserialization.*`, Boot 4는 `spring.jackson.datatype.enum.*`).
- 실패 시나리오: enum은 Jackson 2에서는 `name()`, Jackson 3에서는 `toString()`으로 쓰고 읽으며, `@JsonValue`가 있으면 쓰기와 읽기 모두 그 값을 쓴다. 그래서 상수 이름을 바꾸거나 기존 enum에 `@JsonValue`를 더하면 응답 문자열이 바뀌고, 옛 값을 보내는 클라이언트 요청은 모르는 값이 되어 400(HttpMessageNotReadableException)이 된다. `READ_UNKNOWN_ENUM_VALUES_AS_NULL`을 켜면 오류 대신 필드가 null이 되어 검증 400이나 서비스 계층의 NullPointerException으로 이어진다. 응답 enum에 값을 추가하면, 모르는 값을 예외로 처리하는 클라이언트(Jackson 기본 설정을 쓰는 다른 서버, enum을 엄격하게 디코딩하는 구버전 앱)가 응답 전체를 읽지 못한다.
- 문제가 아닌 경우: 요청에만 쓰는 enum에 값을 더하는 경우(구버전 클라이언트는 새 값을 보내지 않는다). 같은 변경에서 새로 만든 엔드포인트에서만 쓰는 enum. 클라이언트가 모르는 값을 기본값으로 처리한다고 프로젝트 문서에 적혀 있는 경우.
- 고치는 방향: 응답 enum에 값을 더하기 전에 클라이언트의 모르는 값 처리를 확인하고, 처리하지 못하는 구버전에는 기존 값으로 바꿔 내보낸다. 다른 서버의 enum을 받는 쪽이면 `READ_UNKNOWN_ENUM_VALUES_USING_DEFAULT_VALUE`와 `@JsonEnumDefaultValue`로 대비한다. 기존 enum의 직렬화 값을 바꿔야 하면 옛 값도 받게 한다. `@JsonValue`가 없는 enum은 상수에 `@JsonAlias`를 달고, `@JsonValue`가 있거나 새로 더하는 enum은 `@JsonCreator` 팩터리로 옛 값과 새 값을 함께 해석한다. `@JsonValue`가 있으면 `@JsonAlias`가 무시되는 버그(databind#6210)는 Jackson 2.23.0, 3.1.9(2026-11-24 출시), 3.2.5(미출시)에서 고쳐졌으므로, 이보다 낮은 Jackson 버전에서는 이 조합이 동작하지 않는다. Boot 3.x 전체와, Jackson 3.1.8을 관리하는 Boot 4.0.10, 4.1.3, 4.2.0까지가 여기에 든다. 판단은 Boot 버전이 아니라 실제 Jackson 버전으로 한다. 3.3.x에 수정이 들어갔는지는 확인하지 못했다.
- 출처: https://github.com/FasterXML/jackson-databind/wiki/Deserialization-Features, https://github.com/FasterXML/jackson-annotations/wiki/Jackson-Annotations, https://github.com/FasterXML/jackson-annotations/blob/2.x/src/main/java/com/fasterxml/jackson/annotation/JsonAlias.java, https://github.com/FasterXML/jackson-future-ideas/wiki/JSTEP-2, https://docs.spring.io/spring-boot/how-to/spring-mvc.html#howto.spring-mvc.customize-jackson-jsonmapper, https://github.com/FasterXML/jackson-databind/issues/6210, https://github.com/FasterXML/jackson-databind/blob/2.x/release-notes/VERSION-2.x, https://github.com/FasterXML/jackson-databind/blob/3.x/release-notes/VERSION, https://github.com/spring-projects/spring-boot/blob/v4.2.0/gradle.properties, https://github.com/spring-projects/spring-boot/blob/v4.1.3/gradle.properties, https://github.com/spring-projects/spring-boot/blob/v4.0.10/gradle.properties

## 날짜와 시간 형식

- 의심할 코드: 응답이나 요청 필드 타입을 `LocalDateTime`, `OffsetDateTime`, `ZonedDateTime`, `Instant`, `Date` 사이에서 바꾸는 것. `@JsonFormat(pattern = ..., timezone = ...)` 추가나 변경. `spring.jackson.time-zone`, `spring.jackson.date-format` 변경. WRITE_DATES_AS_TIMESTAMPS, ADJUST_DATES_TO_CONTEXT_TIME_ZONE, WRITE_DATES_WITH_CONTEXT_TIME_ZONE 설정 변경(Boot 3는 `spring.jackson.serialization.*`와 `deserialization.*`, Boot 4는 `spring.jackson.datatype.datetime.*`).
- 실패 시나리오: 타임스탬프 쓰기가 꺼진 기본 설정(Boot 3와 Boot 4 모두)에서 `LocalDateTime`은 오프셋 없는 문자열로, `OffsetDateTime`은 값이 가진 오프셋을 붙여서, `Instant`는 UTC(`Z`)로 나간다. 타입을 바꾸면 문자열 모양이 바뀌어 형식을 고정해 파싱하던 앱이 실패하고, 오프셋 없는 값은 기기마다 자기 시간대로 해석되어 시각이 어긋난다. `spring.jackson.time-zone`을 정하면 `Date`뿐 아니라 `OffsetDateTime`과 `ZonedDateTime` 응답도 그 시간대로 바꿔 쓴다(WRITE_DATES_WITH_CONTEXT_TIME_ZONE 기본 켜짐). 요청의 `OffsetDateTime`은 기본으로 문맥 시간대로 조정되어 클라이언트가 보낸 오프셋이 사라진다. 시간대를 지정하지 않으면 Jackson의 문맥 시간대는 JVM 기본값이 아니라 UTC다.
- 문제가 아닌 경우: 응답 DTO의 필드 타입과 `@JsonFormat`은 그대로 두고 내부 계산용 타입만 바꾼 경우. 같은 변경에서 새로 만든 필드나 엔드포인트. 요청에서 기존 형식을 계속 받으면서 받는 형식만 넓히는 경우.
- 고치는 방향: 시각은 `Instant`나 `OffsetDateTime`처럼 오프셋을 포함해 내보내고, 기존 필드의 타입과 형식은 유지한다. 형식을 바꿔야 하면 새 필드를 더한다. 전역 시간대 설정보다 필드 단위 `@JsonFormat`이 영향 범위가 작다.
- 출처: https://github.com/FasterXML/jackson-future-ideas/wiki/JSTEP-2, https://github.com/FasterXML/jackson-databind/blob/3.x/src/main/java/tools/jackson/databind/cfg/DateTimeFeature.java, https://github.com/FasterXML/jackson-databind/blob/2.19/src/main/java/com/fasterxml/jackson/databind/SerializationFeature.java, https://github.com/FasterXML/jackson-databind/wiki/Deserialization-Features, https://github.com/FasterXML/jackson/blob/main/jackson3/MIGRATING_TO_JACKSON_3.md, https://docs.spring.io/spring-boot/how-to/spring-mvc.html#howto.spring-mvc.customize-jackson-jsonmapper

## BigDecimal을 숫자로 쓸지 문자열로 쓸지

- 의심할 코드: 금액이나 비율 필드의 타입을 `double`과 `BigDecimal` 사이에서 바꾸는 것. `@JsonFormat(shape = JsonFormat.Shape.STRING)` 추가나 제거. WRITE_BIGDECIMAL_AS_PLAIN, WRITE_NUMBERS_AS_STRINGS 설정 변경. Boot 3에서 `spring.jackson.generator.write-bigdecimal-as-plain`을 쓰던 프로젝트를 Boot 4로 올리는 것.
- 실패 시나리오: Jackson은 `BigDecimal`을 JSON 숫자로 쓰고, 기본으로는 값이 만들어진 방식에 따라 `1E+3` 같은 지수 표기가 나올 수 있다. JavaScript 클라이언트는 JSON 숫자를 배정밀도 실수로 읽으므로 큰 금액이나 긴 소수의 정밀도와 끝자리 0(`10.50`)을 잃는다. 숫자를 문자열로 바꾸거나 그 반대로 바꾸면 필드의 JSON 타입이 바뀌어, 타입을 엄격하게 디코딩하는 앱 모델이 실패한다. Boot 4.0은 `spring.jackson.generator.*`를 없앴고 WRITE_BIGDECIMAL_AS_PLAIN을 켜는 속성도 없어서, 옛 키가 적용되지 않아 지수 표기가 다시 나올 수 있다. Boot 4.1부터는 `spring.jackson.write.*`로 다시 켤 수 있다.
- 문제가 아닌 경우: 유효 숫자가 15자리 이내이고 클라이언트가 끝자리 0이나 소수 자릿수에 기대지 않는 값을 숫자로 계속 쓰는 경우. 요청에서 문자열과 숫자를 모두 받는 경우(스칼라 강제 변환 ALLOW_COERCION_OF_SCALARS가 기본으로 켜져 있어 문자열 `"10.50"`도 `BigDecimal`로 읽는다). 클라이언트가 JVM 서버뿐인 내부 API.
- 고치는 방향: 새 금액 필드는 처음부터 문자열이나 최소 단위 정수로 정한다. 기존 필드의 JSON 타입은 바꾸지 말고 새 필드를 더한다. 지수 표기가 문제라면 WRITE_BIGDECIMAL_AS_PLAIN을 켜되(Boot 4.0은 customizer로), 전역 설정 변경이므로 위의 전역 설정 항목 기준으로 함께 본다.

## 2^53을 넘는 Long ID

- 의심할 코드: ID 생성 방식을 DB 자동 증가에서 시간 기반 64비트 ID 생성기로 바꾸는 것. 이런 `long` ID를 응답 필드로 새로 내보내는 것. ID 필드의 `@JsonFormat(shape = JsonFormat.Shape.STRING)`이나 `ToStringSerializer`를 지우는 것.
- 실패 시나리오: RFC 8259는 정수가 [-(2^53)+1, (2^53)-1] 범위 안에 있을 때만 구현 간에 값이 정확히 일치한다고 본다. 이 범위를 넘는 `long`을 JSON 숫자로 내보내면 JavaScript 웹 클라이언트가 끝자리를 반올림한 값으로 읽고, 그 값으로 상세 조회나 수정 요청을 보내 다른 리소스를 가리키거나 404를 받는다. 오류 없이 값만 틀어지므로 발견이 늦다.
- 문제가 아닌 경우: DB 자동 증가 ID처럼 값이 2^53보다 충분히 작은 경우. 클라이언트가 JVM 서버뿐인 내부 API. 이미 문자열로 내보내는 ID.
- 고치는 방향: 큰 ID는 `@JsonFormat(shape = JsonFormat.Shape.STRING)`으로 문자열로 내보낸다. 이미 숫자로 나가던 필드를 문자열로 바꾸는 것은 타입 변경이므로 새 필드를 더하거나 API 버전을 나눈다. 요청 쪽은 스칼라 강제 변환이 기본으로 켜져 있어 문자열 `"123"`도 `long`으로 읽는다.
- 출처: https://www.rfc-editor.org/rfc/rfc8259#section-6, https://github.com/FasterXML/jackson-annotations/wiki/Jackson-Annotations, https://github.com/FasterXML/jackson-databind/blob/3.x/src/main/java/tools/jackson/databind/MapperFeature.java

## 전역 naming strategy 변경

- 의심할 코드: `spring.jackson.property-naming-strategy`(SNAKE_CASE, KEBAB_CASE 등) 추가나 변경. 매퍼 빌더에 `PropertyNamingStrategies`를 거는 코드. 공통 부모 DTO나 기존 DTO에 `@JsonNaming` 추가.
- 실패 시나리오: 여러 단어로 된 응답 필드 이름(`orderNo`가 `order_no`로)이 한꺼번에 바뀌어 거의 모든 클라이언트가 깨진다. 요청에서는 기존 클라이언트가 보내는 camelCase 필드가 모르는 속성으로 조용히 버려져 값이 null로 들어간다. 자동 구성 매퍼를 쓰는 HTTP 클라이언트가 다른 서버로 보내는 요청 본문의 이름도 바뀌어 상대 서버가 요청을 해석하지 못한다. 값 없이 단 `@JsonProperty`는 이름을 명시한 것이 아니므로 이 경우에도 이름이 바뀐다.
- 문제가 아닌 경우: 같은 변경에서 새로 만든 DTO에만 `@JsonNaming`을 다는 경우. 클래스에 이미 `@JsonNaming`이 있어 전역 전략이 적용되지 않는 DTO. 모든 필드에 `@JsonProperty("...")`로 이름을 명시한 DTO(ALLOW_EXPLICIT_PROPERTY_RENAMING이 기본으로 꺼져 있어 명시한 이름은 naming strategy가 바꾸지 않는다).
- 고치는 방향: 전역 전략은 바꾸지 않는다. 새 규칙이 필요하면 새 버전 경로의 새 DTO에만 `@JsonNaming`을 적용한다.
- 출처: https://docs.spring.io/spring-boot/appendix/application-properties/index.html, https://github.com/FasterXML/jackson-databind/blob/3.x/src/main/java/tools/jackson/databind/MapperFeature.java, https://docs.spring.io/spring-boot/reference/features/json.html#features.json.jackson2

## 다형 타입의 타입 식별자

- 의심할 코드: `@JsonTypeInfo`의 `use`, `include`, `property` 변경. `@JsonSubTypes.Type`의 `name`이나 `@JsonTypeName` 값 변경. 하위 타입 클래스나 그 바깥 클래스의 이름 변경, 패키지 이동, 중첩 클래스를 밖으로 꺼내는 리팩터링. 응답에 새 하위 타입 추가.
- 실패 시나리오: 타입 식별자는 JSON 계약의 일부다. `Id.CLASS`는 전체 클래스 이름을, `Id.MINIMAL_CLASS`는 패키지 일부를 식별자로 쓰므로 리팩터링으로 패키지를 옮기면 식별자가 바뀐다. `Id.NAME`에서 이름을 명시하지 않으면 패키지를 뺀 클래스 이름(중첩 클래스면 `Payment$Card` 형태)이 식별자라서 클래스 이름 변경이 곧 계약 변경이다. 옛 식별자를 보내는 클라이언트 요청은 하위 타입을 찾지 못해 400이 된다(FAIL_ON_INVALID_SUBTYPE 기본 켜짐). 응답에 새 식별자가 나오면 그 하위 타입을 모르는 클라이언트가 응답 전체를 읽지 못한다.
- 문제가 아닌 경우: `Id.NAME`을 쓰면서 `@JsonSubTypes.Type(name = "CARD")`나 `@JsonTypeName`으로 이름을 명시한 채 클래스 이름만 바꾼 경우. `Id.CLASS`와 `Id.MINIMAL_CLASS`는 명시한 이름을 쓰지 않으므로 이 조건에 들지 않는다. 같은 변경에서 새로 만든 다형 타입. 요청으로만 쓰는 타입에 하위 타입을 추가하는 경우.
- 고치는 방향: `Id.NAME`과 명시적 이름을 쓰고 이름은 바꾸지 않는다. 모르는 식별자에 대비해야 하면 `defaultImpl`을 둔다. 응답 하위 타입 추가는 enum 값 추가와 같은 기준으로 본다.
- 출처: https://github.com/FasterXML/jackson-annotations/blob/2.x/src/main/java/com/fasterxml/jackson/annotation/JsonTypeInfo.java, https://github.com/FasterXML/jackson-annotations/blob/2.x/src/main/java/com/fasterxml/jackson/annotation/JsonTypeName.java, https://github.com/FasterXML/jackson-databind/wiki/Deserialization-Features

## 모르는 필드 거부 설정과 요청 필드 제거

- 의심할 코드: `spring.jackson.deserialization.fail-on-unknown-properties=true`, 매퍼 빌더의 FAIL_ON_UNKNOWN_PROPERTIES 켜기, Boot 3에서 `new ObjectMapper()`나 Jackson 2 `JsonMapper.builder().build()`로 만든 매퍼 빈으로 교체해 Jackson 2 기본값(켜짐)으로 돌아간 상태(자동 구성 빌더나 Spring `Jackson2ObjectMapperBuilder`로 만든 매퍼는 꺼진 채다. Boot 4에서 `JsonMapper.builder().build()`로 바꾸면 Jackson 3 기본값이라 거부하지 않는다). 이런 설정이 있는 프로젝트에서 요청 DTO의 필드를 지우거나 이름을 바꾸는 것. Boot 4.0.0부터 4.0.5까지의 `spring.jackson.use-jackson2-defaults=true`.
- 실패 시나리오: 모르는 필드를 거부하면, 서버가 지운 필드를 계속 보내는 구버전 앱과 다른 서버의 요청이 모두 400이 된다. 방향을 바꿔 보면, 응답에 필드를 추가할 때 모르는 키를 거부하도록 응답을 디코딩하는 클라이언트(Jackson 2 기본값의 `ObjectMapper`를 쓰는 다른 서버, 엄격하게 디코딩하는 구버전 앱)가 실패한다.
- 문제가 아닌 경우: Boot 3와 Boot 4의 기본 설정(거부하지 않음)에서 요청 필드를 지우는 것은 400을 만들지 않는다. 다만 클라이언트가 보내던 값이 조용히 버려지므로 그 값에 기대던 동작이 없는지 본다. 응답을 읽는 쪽이 Boot 기본 매퍼나 Jackson 3 기본값(FAIL_ON_UNKNOWN_PROPERTIES 꺼짐)을 쓰는 서버인 경우.
- 고치는 방향: 거부 설정을 유지해야 하면 지운 필드를 `@JsonIgnoreProperties({"couponCode"})`처럼 무시 목록에 남긴다. 명시적으로 무시한 속성은 FAIL_ON_IGNORED_PROPERTIES가 기본으로 꺼져 있어 조용히 건너뛴다. 클라이언트가 옮겨 간 뒤 목록에서 뺀다.
