# Spring Web 참조

적용 버전: Spring Boot 3.x(Spring Framework 6.x)와 Spring Boot 4.x(Spring Framework 7.x), Spring MVC 기준. 버전에 따라 결론이 다른 곳은 항목 안에 버전을 적었다.

## 요청 DTO에 검증 제약 추가

- 의심할 코드: 기존 요청 DTO 필드에 `@NotNull`, `@NotBlank`, `@NotEmpty`, `@Size`, `@Min`, `@Max`, `@Pattern`을 더하거나 범위를 좁히는 것. 기존 `@RequestBody` 파라미터에 `@Valid`나 `@Validated`를 더하는 것. 중첩 객체 필드에 `@Valid`를 더하는 것. `@RequestParam`, `@PathVariable` 파라미터에 제약 어노테이션을 직접 다는 것. 컨트롤러 클래스에 `@Validated`를 더하거나 지우는 것.
- 실패 시나리오: `@Valid`가 붙은 `@RequestBody`(컬렉션이 아닌 객체)가 검증에 실패하면 MethodArgumentNotValidException이, 메서드 파라미터에 직접 단 제약이나 jakarta `@Valid`를 단 `List`, 배열, `Map` 본문(`@Valid @RequestBody List<...>`)이 실패하면 HandlerMethodValidationException이 나고 둘 다 400이다. 파라미터에 jakarta `@Valid`를 단 `Set` 같은 다른 컬렉션 본문과 Spring `@Validated`만 단 컬렉션 본문은 검증되지 않는다. 다만 타입 인자에 단 원소 어노테이션(`List<@NotBlank String>`, `Set<@Valid Item>`)은 컬렉션 종류와 상관없이 메서드 검증을 켜서 HandlerMethodValidationException(400)이 난다(버전 범위는 아래). 그동안 빈 값이나 긴 문자열을 보내도 성공하던 구버전 앱의 요청이 배포 직후 400으로 바뀐다. Spring Framework 6.1(Boot 3.2)부터는 클래스에 `@Validated`가 없어도 파라미터에 직접 단 제약이 검증되므로, 업그레이드만으로 그동안 동작하지 않던 제약이 켜질 수 있다. 본문은 버전마다 범위가 다르다. 6.1.0부터 `@Valid`를 단 `List`, 6.1.3부터 배열, `Map`, 원소 제약, 6.1.9부터 원소 `@Valid`가 검증된다. `Set` 원소의 위반은 6.1.11부터 400이고, 그 전에는 위반을 결과로 옮기지 못해 IllegalStateException으로 500이 된다. 반대로 컨트롤러 클래스에 `@Validated`가 있으면 AOP 프록시로 검증되어 기본으로 `jakarta.validation.ConstraintViolationException`이 나고(Boot 3.5부터 있는 `spring.validation.method.adapt-constraint-violations=true`이면 MethodValidationException), 둘 다 기본 처리에서 500이다. `@Valid @RequestBody`가 있는 메서드에 파라미터 제약을 하나만 더해도 본문 검증까지 메서드 검증으로 넘어가 예외가 HandlerMethodValidationException으로 바뀌므로, MethodArgumentNotValidException만 처리하던 advice의 오류 본문과 상태 코드가 달라진다.
- 문제가 아닌 경우: 같은 변경에서 새로 만든 엔드포인트나 DTO. 필드 제약만 더했고 그 DTO를 받는 모든 엔드포인트에 `@Valid`, `@Validated`, 파라미터 제약이 없으며 서비스 계층에서도 그 DTO를 검증하지 않는 경우(diff에 보이는 엔드포인트 하나가 아니라 DTO의 모든 사용처를 확인한다). 서비스 계층이 이미 같은 조건으로 같은 상태 코드를 돌려주고 있는 경우(오류 본문 형식이 바뀌는지는 따로 본다).
- 고치는 방향: 기존 필드의 제약 강화는 클라이언트가 실제로 보내는 값을 확인한 뒤 적용한다. 새로 필수가 되는 값은 한동안 서버 기본값으로 채우고 클라이언트가 옮겨 간 뒤 필수로 바꾸거나, 새 버전 엔드포인트에만 둔다. 오류 처리 advice는 MethodArgumentNotValidException과 HandlerMethodValidationException을 함께 처리하고, 클래스에 `@Validated`를 쓰는 컨트롤러가 있으면 ConstraintViolationException도 처리한다.

## @RequestParam, @RequestHeader의 기본 required

- 의심할 코드: 기존 핸들러 메서드에 `@RequestParam`이나 `@RequestHeader` 파라미터를 더하는 것. 기존 파라미터에서 `required = false`, `defaultValue`, `Optional` 래퍼, `@Nullable`을 지우는 것. 파라미터의 `name`이나 `value`를 바꾸는 것. 선택 파라미터의 타입을 래퍼에서 원시 타입(`int`, `long`)으로 바꾸는 것. 어노테이션 없이 `int page` 같은 단순 타입 파라미터를 더하는 것.
- 실패 시나리오: 두 어노테이션 모두 `required` 기본값이 true다. 새 파라미터를 더하면 그 값을 보내지 않는 기존 호출이 MissingServletRequestParameterException이나 MissingRequestHeaderException으로 400이 된다. 이름을 바꿔도 옛 이름으로 보내는 클라이언트는 값이 없는 것으로 처리되어 같은 400을 받는다. 구버전 앱이나 헤더를 붙이지 않는 다른 서버가 이 경우에 해당한다. `required = false`라도 타입이 `int`나 `long` 같은 원시 타입이고 `defaultValue`가 없으면, 값이 빠진 요청에서 null을 넣지 못해 IllegalStateException이 나고 500이 된다(`boolean`만 false로 채워진다). 어노테이션 없는 단순 타입 파라미터는 `required = false`인 `@RequestParam`으로 처리되므로 원시 타입이면 같은 500이 난다.
- 문제가 아닌 경우: `required = false`(래퍼 타입일 때), `defaultValue`(지정하면 required가 자동으로 false가 된다), `Optional`로 선언한 새 파라미터. `@Nullable`을 단 파라미터와 Kotlin의 널 가능 타입은 required가 기본값이어도 선택으로 처리된다. 다만 JSpecify `@Nullable`은 Spring Framework 7(Boot 4)부터 인식되고, 6.x(Boot 3)에서는 Spring이나 Jakarta 같은 선언 어노테이션만 인식된다. `@RequestHeader` 이름의 대소문자만 바꾼 경우(헤더 이름은 대소문자를 구분하지 않는다). 같은 변경에서 새로 만든 엔드포인트. 앞단의 게이트웨이나 필터가 그 헤더를 모든 요청에 붙인다고 프로젝트 문서에 적힌 경우.
- 고치는 방향: 기존 엔드포인트에 더하는 파라미터는 래퍼 타입의 선택 파라미터로 두거나 기본값을 정한다. 필수로 만들어야 하면 클라이언트가 값을 보내기 시작한 것을 확인한 뒤 바꾼다.
- 출처: https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/requestparam.html, https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/bind/annotation/RequestParam.html, https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/bind/annotation/RequestHeader.html, https://github.com/spring-projects/spring-framework/blob/main/spring-web/src/main/java/org/springframework/web/method/annotation/AbstractNamedValueMethodArgumentResolver.java, https://github.com/spring-projects/spring-framework/blob/main/spring-core/src/main/java/org/springframework/core/MethodParameter.java, https://github.com/spring-projects/spring-framework/blob/v6.2.0/spring-core/src/main/java/org/springframework/core/MethodParameter.java, https://github.com/spring-projects/spring-framework/blob/main/spring-web/src/main/java/org/springframework/web/method/annotation/RequestParamMethodArgumentResolver.java, https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/servlet/mvc/support/DefaultHandlerExceptionResolver.html, https://www.rfc-editor.org/rfc/rfc9110#section-5.1

## 경로, HTTP 메서드, Content-Type 변경

- 의심할 코드: `@RequestMapping`, `@GetMapping` 등의 경로 문자열 변경, 클래스 단위 `@RequestMapping` 접두사 변경, `@PathVariable` 위치 변경. `@GetMapping`을 `@PostMapping`으로 바꾸는 등 HTTP 메서드 변경. `consumes`, `produces`를 더하거나 좁히는 것. `server.servlet.context-path`, `spring.mvc.servlet.path` 변경.
- 실패 시나리오: 옛 경로 호출은 404, 메서드가 바뀌면 405(HttpRequestMethodNotSupportedException)가 된다. `consumes`를 좁히면 다른 Content-Type으로 보내던 클라이언트가 415, `produces`를 좁히면 Accept가 맞지 않는 클라이언트가 406을 받는다. 클래스 접두사나 context-path 변경은 그 아래 모든 엔드포인트를 한꺼번에 옮긴다. 구버전 앱은 강제 업데이트 전까지 옛 경로와 메서드로 계속 호출한다.
- 문제가 아닌 경우: 같은 변경에서 새로 만든 엔드포인트. 옛 매핑을 남겨 둔 채 새 매핑을 더한 경우(`@GetMapping({"/orders", "/v2/orders"})`). 프로젝트 문서에 외부 클라이언트가 호출하지 않는다고 적힌 내부 경로.
- 고치는 방향: 옛 경로와 메서드를 남겨 같은 서비스를 호출하게 하고, 사용 중단을 알린 뒤 호출이 사라지면 지운다.
- 출처: https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-requestmapping.html, https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/servlet/mvc/support/DefaultHandlerExceptionResolver.html, https://docs.spring.io/spring-boot/appendix/application-properties/index.html

## 상태 코드 변경

- 의심할 코드: `@ResponseStatus` 추가나 변경. `ResponseEntity.ok()`를 `created()`, `noContent()`, `accepted()`로 바꾸거나 그 반대. 조회 결과가 없을 때 404를 내던 코드를 200과 빈 값(null 본문, 빈 객체, 빈 배열)으로 바꾸는 것. `ResponseEntity.of(Optional)`이나 `ofNullable`을 도입해 200이던 응답을 404로 바꾸는 것.
- 실패 시나리오: 상태 코드를 200과 같은지로 비교하는 구버전 앱은 201이나 204를 실패로 처리한다. 204는 본문이 없다는 뜻이므로(RFC 9110) 본문을 파싱하던 클라이언트가 실패한다. 404를 "없음" 화면으로 처리하던 클라이언트는 200과 빈 본문을 받으면 null 참조 오류나 빈 화면을 낸다. 반대로 200과 빈 값을 정상으로 처리하던 클라이언트는 404를 받으면 오류 처리 경로로 빠진다.
- 문제가 아닌 경우: 같은 변경에서 새로 만든 엔드포인트. 상태 코드는 그대로이고 본문에 필드만 더하는 경우. 클라이언트가 2xx 전체를 성공으로 처리한다고 프로젝트 문서에 적힌 경우(204로 바꿀 때는 본문 파싱 여부를 따로 본다).
- 고치는 방향: 기존 엔드포인트의 상태 코드는 유지한다. 의미를 바로잡아야 하면 새 버전 엔드포인트에서 바꾼다.
- 출처: https://www.rfc-editor.org/rfc/rfc9110#section-15.3.2, https://www.rfc-editor.org/rfc/rfc9110#section-15.3.5, https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/http/ResponseEntity.html

## 오류 응답 형식과 ProblemDetail

- 의심할 코드: `spring.mvc.problemdetails.enabled` 변경. `ResponseEntityExceptionHandler`를 상속한 advice 추가나 제거. `@ExceptionHandler`가 돌려주는 타입을 자체 오류 DTO에서 `ProblemDetail`이나 `ErrorResponse`로 바꾸는 것과 그 반대. `ErrorAttributes`나 `ErrorController` 교체. Boot 4로 올리면서 `server.error.include-message`, `server.error.include-binding-errors` 같은 키를 그대로 두는 것. Spring Framework 7.1(Boot 4.2)의 `WebMvcConfigurer.configureProblemDetails`에서 `renderUnhandledExceptions(true)`를 켜는 것, 또는 7.1로 올리는 빌드 변경.
- 실패 시나리오: Boot 기본 오류 응답은 `/error`가 만드는 JSON(timestamp, status, error, path 등)이다. `spring.mvc.problemdetails.enabled=true`를 켜면 Spring MVC 내장 예외(검증 실패, 405, 415 등)의 응답이 RFC 9457 형식(type, title, status, detail, instance)과 `application/problem+json` 미디어 타입으로 바뀐다. Boot가 등록하는 이 핸들러는 순서가 0이라서, 순서를 정하지 않은(가장 낮은 우선순위) 기존 advice가 같은 내장 예외를 처리하고 있어도 Boot 핸들러가 먼저 잡는다. 그래서 `error`나 자체 `code` 필드를 읽어 메시지를 보여 주거나 재시도를 판단하던 클라이언트의 오류 처리가 깨진다. 7.1의 `renderUnhandledExceptions(true)`는 처리되지 않은 모든 예외를 ProblemDetail로 바꾼다. Boot 4.0은 `server.error.*`를 `spring.web.error.*`로 옮겼으므로 옛 키를 두면 기본값(never)으로 돌아가 `/error` 본문에서 message와 errors가 사라진다. Spring Framework 7.1부터는 ProblemDetail의 `instance`에 요청 경로를 넣지 않으므로 그 값을 읽던 클라이언트가 값을 잃는다.
- 문제가 아닌 경우: `ResponseEntityExceptionHandler`를 상속한 advice 빈이 이미 있으면 Boot의 problemdetails 핸들러는 등록되지 않으므로 설정만 바꾼 diff는 응답을 바꾸지 않는다. 기존 자체 advice가 `@Order`로 0보다 작은 순서(더 높은 우선순위)를 가진 경우이되, 그 advice가 처리하는 예외에만 해당한다(처리하지 않는 내장 예외는 여전히 ProblemDetail로 바뀌고, 같은 0이면 순서가 정해지지 않는다). 같은 변경에서 새로 만든 API가 처음부터 ProblemDetail을 쓰는 경우. 기존 오류 본문에 필드를 더하기만 하는 경우.
- 고치는 방향: API 전체의 오류 형식을 하나로 정하고, 바꿀 때는 기존 필드를 함께 내보내는 기간을 둔다. ProblemDetail의 `properties` 맵에 넣은 값은 최상위 JSON 필드로 펼쳐지므로 기존 `code` 같은 필드를 유지할 수 있다. 자체 advice로 내장 예외를 처리하려면 Boot 핸들러보다 앞서도록 순서를 정한다.
- 출처: https://docs.spring.io/spring-boot/reference/web/servlet.html#web.servlet.spring-mvc.error-handling, https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html, https://www.rfc-editor.org/rfc/rfc9457, https://docs.spring.io/spring-boot/api/java/org/springframework/boot/webmvc/error/DefaultErrorAttributes.html, https://docs.spring.io/spring-boot/appendix/application-properties/index.html, https://github.com/spring-projects/spring-boot/blob/v4.0.0/module/spring-boot-webmvc/src/main/java/org/springframework/boot/webmvc/autoconfigure/WebMvcAutoConfiguration.java, https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Configuration-Changelog, https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-7.1-Release-Notes

## @ControllerAdvice 변경의 범위

- 의심할 코드: `@ControllerAdvice`나 `@RestControllerAdvice` 클래스의 `@ExceptionHandler` 추가, 변경, 삭제. `basePackages`, `annotations`, `assignableTypes` 속성을 바꾸거나 지우는 것. 새 advice 추가나 `@Order` 변경. advice에 `ResponseBodyAdvice` 구현을 더하는 것(모든 응답을 `{"data": ...}`로 감싸는 등). 전역 `@InitBinder`, `@ModelAttribute` 메서드.
- 실패 시나리오: 범위 속성이 없는 advice는 모든 컨트롤러에 적용된다. diff에는 advice 파일 하나만 보이지만 범위 안 모든 엔드포인트의 오류 상태 코드와 본문이 함께 바뀐다. `@ExceptionHandler` 처리는 Spring MVC 내장 예외를 상태 코드로 바꾸는 기본 처리보다 먼저 돌기 때문에, `@ExceptionHandler(Exception.class)`를 더하면 그동안 400, 405, 415로 나가던 내장 예외까지 그 핸들러가 정한 상태(흔히 500)로 바뀐다. 예외의 구체성 비교는 advice 하나 안에서만 하고 advice 사이에서는 우선순위가 먼저다. 그래서 우선순위가 더 높은 advice의 넓은 핸들러는 다른 advice의 구체적인 핸들러를 가로채고, 둘 다 순서가 없으면 어느 쪽이 먼저인지 정해지지 않는다. `ResponseBodyAdvice`로 응답을 감싸면 모든 성공 응답의 최상위 구조가 바뀐다.
- 문제가 아닌 경우: `basePackages`나 `assignableTypes`로 같은 변경에서 새로 만든 컨트롤러에만 한정한 advice. 기존 핸들러에서 로그만 바꾸고 상태 코드와 본문은 같은 경우. 더 구체적인 핸들러가 같은 advice 안이나 컨트롤러 안, 또는 더 높은 우선순위의 advice에 있어 새 핸들러가 잡을 예외가 없는 경우.
- 고치는 방향: advice에는 범위 속성과 `@Order`를 명시한다. 바꾼 advice가 닿는 대표 예외(검증 실패, 없는 리소스, 지원하지 않는 메서드, 서버 오류)의 상태 코드와 본문을 테스트로 고정한다.
- 출처: https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-advice.html, https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-exceptionhandler.html, https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/servlet/mvc/method/annotation/ResponseBodyAdvice.html, https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/servlet/config/annotation/WebMvcConfigurationSupport.html

## Spring Data Page 응답의 JSON 형식

- 의심할 코드: 컨트롤러가 `Page<T>`를 그대로 반환하는 것. `@EnableSpringDataWebSupport(pageSerializationMode = VIA_DTO)` 추가, `spring.data.web.pageable.serialization-mode` 변경, 반환 타입을 `Page`에서 `PagedModel`로 바꾸는 것. `spring.data.web.pageable.one-indexed-parameters` 변경.
- 실패 시나리오: 기본 모드(DIRECT)에서 `Page`는 구현 클래스 `PageImpl`의 getter 그대로 직렬화된다. Spring Data는 `PageImpl`이 도메인 타입이라 다른 이유로 API가 바뀔 수 있고 그러면 JSON이 깨질 수 있다고 밝히며, 3.1부터 경고 로그를 낸다. VIA_DTO로 바꾸거나 `PagedModel`로 감싸면 형식이 `content`와 `page`(size, totalElements, totalPages, number) 두 필드로 바뀐다. 최상위의 `totalElements`나 `last` 같은 필드를 읽던 클라이언트의 페이지 처리가 깨지고, 설정으로 바꾸면 `Page`를 반환하는 모든 엔드포인트가 한꺼번에 바뀐다. `one-indexed-parameters`를 바꾸면 모든 페이지 요청의 page 번호 해석이 한 칸 밀린다.
- 문제가 아닌 경우: 같은 변경에서 새로 만든 엔드포인트가 처음부터 `PagedModel`이나 전용 응답 DTO를 쓰는 경우. 이미 전용 페이지 DTO로 변환해 내보내고 있어 모드 설정이 닿지 않는 경우. 기본 모드는 Spring Data 4.x와 Boot 4에서도 DIRECT라서 업그레이드만으로 형식이 VIA_DTO로 바뀌지는 않는다.
- 고치는 방향: 기존 응답 형식을 그대로 담는 전용 DTO로 변환해 내보내고, 새 엔드포인트는 `PagedModel`이나 전용 DTO로 시작한다. 전역 모드 변경은 클라이언트 전환 일정과 함께 한다.
- 출처: https://docs.spring.io/spring-data/commons/reference/repositories/core-extensions.html#core.web.page, https://github.com/spring-projects/spring-data-commons/blob/main/src/main/java/org/springframework/data/web/config/EnableSpringDataWebSupport.java, https://docs.spring.io/spring-boot/appendix/application-properties/index.html

## 경로 끝 슬래시 매칭

- 의심할 코드: Spring Boot 2.x에서 3.x로 올리는 빌드 변경. `PathMatchConfigurer.setUseTrailingSlashMatch(true)`를 지우는 것(Spring Framework 7에서 컴파일되지 않아 지우는 경우 포함). `UrlHandlerFilter` 제거나 적용 경로, 리다이렉트 상태 코드 변경.
- 실패 시나리오: Spring Framework 6.0부터 끝 슬래시 매칭 기본값이 false라서 `GET /orders/`는 `@GetMapping("/orders")`에 맞지 않고 404가 된다. 끝 슬래시를 붙여 호출하던 구버전 앱이나 다른 서버가 깨진다. 6.x에서 deprecated 옵션을 켜 두었던 프로젝트는 Spring Framework 7(Boot 4)에서 그 옵션이 제거되어 같은 문제를 만난다. `UrlHandlerFilter`를 301이나 302 리다이렉트로 설정하면 클라이언트가 POST를 GET으로 바꿔 다시 보낼 수 있어(RFC 9110) 요청 본문이 사라진다.
- 문제가 아닌 경우: 끝 슬래시 매칭을 켠 적이 없는 프로젝트에서 Boot 3 이상으로 처음 만든 엔드포인트(끝 슬래시 요청은 원래 404였다). 같은 변경에서 `UrlHandlerFilter`로 요청을 감싸 처리하도록 바꿨고, 적용 경로에 합친 경로가 끝 슬래시로 끝나는 매핑이 없는 경우. 307, 308 리다이렉트로 바꾼 경우는 호출자가 브라우저이거나 POST 리다이렉트를 따르는 클라이언트일 때만 해당한다.
- 고치는 방향: 끝 슬래시 호출이 남아 있으면 `UrlHandlerFilter`로 요청을 감싼다(`wrapRequest()`). 308 리다이렉트는 브라우저 대상 경로에만 쓴다. Spring의 `SimpleClientHttpRequestFactory`처럼 GET에서만 리다이렉트를 따르는 클라이언트는 POST에 308을 그대로 받고, RestTemplate 기본 오류 처리는 4xx와 5xx만 오류로 보므로 실패가 드러나지 않는다. 필터는 루트 `/`를 처리하지 않는다. 타입 단위 접두사(`@RequestMapping("/orders")`) 아래 메서드 단위 `@GetMapping("/")`처럼 합친 경로가 끝 슬래시로 끝나는 매핑(`/orders/`)은 필터를 걸면 매핑되지 않으므로, 경로 없는 `@GetMapping`으로 바꾼다. 클래스 단위 `@RequestMapping("/")`는 메서드 경로와 합쳐도 끝 슬래시가 생기지 않으므로 해당하지 않는다. `UrlHandlerFilter`는 Spring Framework 6.2(Boot 3.4)부터 있으므로 그보다 낮은 버전에서는 매핑에 두 경로를 모두 적는다. 보안 규칙의 경로 매칭과 어긋나지 않는지 함께 본다.

## Spring Framework 7의 API 버전 지정

- 의심할 코드: `spring.mvc.apiversion.*` 추가(`use.header`, `use.query-parameter`, `use.path-segment`, `use.media-type-parameter`, `required`, `default`, `supported`). `WebMvcConfigurer.configureApiVersioning` 구현. 기존 매핑이나 새 매핑에 `version = "1.1"`이나 기준 버전 `version = "1.2+"`를 더하는 것.
- 실패 시나리오: 버전 지정을 켜면 기본으로 버전이 필수가 되어, 버전을 보내지 않는 기존 클라이언트가 모두 400(MissingApiVersionException)을 받는다. 지원하지 않는 버전은 400(InvalidApiVersionException)이다. 지원 버전 목록은 기본으로 매핑에 적힌 버전에서 만들어지므로, 매핑에 적지 않은 버전을 보내는 클라이언트도 400을 받는다. 초기 버전뿐 아니라 기준 버전 매핑 사이의 버전도 같다(`"1.2+"` 매핑만 있을 때 1.3 요청은 1.3이 매핑이나 `supported`에 없으면 400). 경로 세그먼트 방식은 URL 자체를 바꾸고, 버전 없는 경로는 기본 버전을 정해도 InvalidApiVersionException이 된다(버전 없는 경로를 가리는 Predicate를 설정한 경우만 예외이고, 이 Predicate는 Spring Framework 7.0.6(Boot 4.0.4)부터 `WebMvcConfigurer`로만 설정할 수 있다). 기본 버전을 정하면 버전 없는 요청은 그 버전을 보낸 것으로 처리되므로, 기본 버전에 맞는 고정 버전 매핑이나 기본 버전 이하의 기준 버전 매핑을 더하면 버전을 보내지 않는 구버전 앱이 새 메서드로 옮겨 간다. 기본 버전 없이 `required=false`만 두면 버전 없는 요청에 가장 최신 버전이 쓰이므로, 기존 메서드에 version을 달면 구버전 앱이 최신 메서드로 옮겨 간다. 기준 버전 매핑(`1.2+`)을 새로 더하면 그 버전 이상을 보내는 기존 클라이언트도 새 메서드로 옮겨 간다. 고정 버전 매핑(`"1.5"`)을 낮은 기준 버전 매핑이나 버전 없는 매핑이 있는 경로에 더하면, 그보다 높은 버전(1.6)을 보내던 요청이 새 고정 매핑에 가려져 400(NotAcceptableApiVersionException)이 된다.
- 문제가 아닌 경우: 헤더, 쿼리 파라미터, 미디어 타입 파라미터 방식에서 기본 버전을 현재 동작으로 정했고, 새로 더한 매핑이 기본 버전보다 높은 기준 버전(`+`) 매핑이며 그 버전 이상을 보내는 클라이언트가 아직 없는 경우. 고정 버전 매핑은 그보다 높은 버전을 보내는 클라이언트가 없을 때만 이 조건에 든다. Spring Framework 6.x(Boot 3)에는 이 기능이 없으므로 해당하지 않는다.
- 고치는 방향: 기존 API에 버전 지정을 들일 때는 기본 버전을 현재 동작으로 정하고, 초기 버전을 포함해 클라이언트가 보내는 모든 버전을 `supported`에 명시한다. 버전 매핑을 더할 때는 그 버전을 보내는 클라이언트뿐 아니라 기본 버전이나 최신 버전으로 처리되는 버전 없는 클라이언트까지 어느 메서드로 가는지 따진다.
- 출처: https://docs.spring.io/spring-framework/reference/web/webmvc-versioning.html, https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-requestmapping.html#mvc-ann-requestmapping-version, https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/servlet/config/annotation/ApiVersionConfigurer.html, https://docs.spring.io/spring-boot/reference/web/servlet.html#web.servlet.spring-mvc.api-versioning, https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-7.0-Release-Notes, https://github.com/spring-projects/spring-framework/blob/v7.0.6/spring-web/src/main/java/org/springframework/web/accept/PathApiVersionResolver.java, https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/accept/NotAcceptableApiVersionException.html

## 컨트롤러가 비즈니스 규칙과 트랜잭션을 직접 갖는 것

- 의심할 코드: `@RestController` 클래스나 메서드의 `@Transactional`. 컨트롤러가 리포지토리를 둘 이상 주입받아 조회와 저장을 섞어 호출하는 것. 컨트롤러 안의 상태 전이 판단(`if (order.getStatus() == OrderStatus.PAID)`), 금액 계산, 재고 차감 같은 업무 규칙.
- 실패 시나리오: Spring Data 리포지토리의 CRUD 메서드는 각자 트랜잭션으로 돈다. 컨트롤러에서 `orderRepository.save(...)`와 `memberRepository.save(...)`를 차례로 부르다 두 번째가 실패하면 첫 번째만 커밋되어 데이터가 어긋난다. 업무 규칙이 컨트롤러에 있으면 배치나 메시지 소비자 같은 다른 진입점이 같은 규칙을 복사하게 되고, 한쪽만 고쳐지는 일이 생긴다. 컨트롤러에 둔 트랜잭션 경계도 HTTP 밖의 진입점에서 재사용할 수 없다.
- 문제가 아닌 경우: 리포지토리 하나로 조회만 하고 DTO로 바꿔 돌려주는 단순 조회. 입력 형식 검사, 인증 정보 꺼내기, 응답 변환처럼 HTTP에 속한 로직. 프로젝트 규칙 문서가 이 구조를 허용하는 경우.
- 고치는 방향: 여러 리포지토리를 묶는 작업과 업무 규칙은 `@Service`로 옮기고 그 메서드에 트랜잭션 경계를 둔다. 컨트롤러는 요청 변환, 서비스 호출, 응답 변환만 맡는다.
- 출처: https://docs.spring.io/spring-data/jpa/reference/jpa/transactions.html, https://docs.spring.io/spring-framework/reference/core/beans/classpath-scanning.html#beans-stereotype-annotations

## 엔티티를 그대로 응답하거나 요청으로 받는 것

- 의심할 코드: 컨트롤러 반환 타입이나 `@RequestBody` 타입이 `@Entity` 클래스, 그 컬렉션, `Page<엔티티>`인 것. `@ModelAttribute`나 어노테이션 없는 파라미터로 엔티티를 받아 폼이나 쿼리 파라미터를 바인딩하는 것. 엔티티에 `@JsonIgnore`, `@JsonManagedReference`, `@JsonBackReference`, `@JsonIdentityInfo`를 다는 것. 컨트롤러 변경 없이 그런 엔티티의 필드를 더하거나 이름을 바꾸는 diff.
- 실패 시나리오: 엔티티 필드를 바꾸면 응답 JSON도 함께 바뀌어 내부 리팩터링이 곧 API 변경이 된다. 지연 로딩 연관을 직렬화하면, Boot 기본값(`spring.jpa.open-in-view=true`)에서는 직렬화 도중 쿼리가 추가로 나가고, open-in-view를 끄면 직렬화 도중 지연 로딩이 실패해 JSON을 쓰지 못하고 500이 된다(HttpMessageNotWritableException은 500으로 처리된다). 양방향 연관은 서로를 따라가며 직렬화가 끝나지 않아 실패한다. 엔티티를 요청으로 받으면 클라이언트가 `id`, `role`, `status`처럼 받을 생각이 없던 필드까지 채울 수 있다(대량 할당). Spring 문서는 폼과 쿼리 파라미터 바인딩에서 JPA 엔티티가 안전하지 않다고 보고, `@RequestBody`도 Jackson이 엔티티의 설정 가능한 속성을 모두 채우므로 같은 위험이 있다.
- 문제가 아닌 경우: 같은 변경이 엔티티 반환을 전용 DTO로 바꾸는 경우. 프로젝트 규칙 문서가 엔티티 노출을 허용하고, 그 엔티티에 연관과 민감 필드가 없는 경우(그래도 내부 변경이 API 변경이 되는 점은 Suggestion으로 남길 수 있다).
- 고치는 방향: 요청과 응답은 전용 DTO(record 등)로 주고받고, 요청 DTO에는 클라이언트가 바꿀 수 있는 필드만 둔다. 폼과 쿼리 파라미터로 엔티티를 받는 코드를 당장 없앨 수 없으면 `@InitBinder`의 `setAllowedFields`로 바인딩할 필드를 제한한다(`@RequestBody`에는 적용되지 않는다). 지연 로딩이 필요한 데이터는 서비스의 트랜잭션 안에서 DTO로 옮긴다.
